A personal field guide · entry level

How to vibe code —
without losing the plot.

A workflow for shipping AI-assisted projects with Codex, Claude, Cursor, and the GSD repo — using a tailored scaffold so every CLI finds the same context.

One way, not the only way. This is the workflow I'm currently using to keep AI coding projects on the rails. Treat it as a starting point — swap, skip, or rearrange anything that doesn't serve your project. The point is having a process, not following this process.

00

Setup (do this once)

Get the boring stuff out of the way so future-you can move fast.

  1. Install an AI CLI tool. Pick at least one — Codex, Claude Code, or both. If you'll use GSD with Codex, your Codex CLI must be 0.130.0 or newer (older versions cause duplicate skill listings). You can run multiple CLIs on the same project; just keep one driver per branch at a time.
  2. Set up Git. A GitHub account (personal or company) gives you a rolling cloud backup. Pure local git works too — it's better than nothing. Follow GitHub's official setup: docs.github.com/en/get-started/git-basics/set-up-git. Commit early, commit often. Git is the only memory layer your AI can't lose.
  3. Save your templates somewhere you can grab them. Your scaffold .zip and your prompt-handoff.md. Same place every time — Desktop, Drive, a dotfiles repo. The scaffold encodes how every CLI will read your project. Reuse it.
01

Ideate. Get it out of your head.

The idea is messy in your head. Make it messy on a page first, so the AI has something to work with.

  1. Open any general chat AI (Claude.ai, ChatGPT, anything). Talk through your idea until you have a clear picture: what it does, who it's for, what v1 must include, what's out of scope.
  2. Ask for a structured write-up. Tell it to produce a single markdown document: one-liner, problem, audience, must-haves, nice-to-haves, constraints, and explicit non-goals. Save it as idea.md. This is your idea document. It's what you'll feed the bootstrap step next — different from the handoff.md inside the scaffold, which tracks state between sessions.
02

Bootstrap. Pre-seed the scaffold.

Take your idea + a blank scaffold and let the AI fill in the planning docs before any code exists.

  1. Start a fresh chat session. Attach three things: (a) the scaffold zip, (b) your idea.md, (c) paste prompt-handoff.md as your first message.
  2. Let the AI inspect and ask. It should first prove it read the scaffold (the prompt forces this), then ask a tight round of clarifying questions — stack, v1 scope, GSD mode, which CLIs you'll use.
  3. Answer, then let it populate. It fills in AGENTS.md, the planning docs, the first feature spec, and the GSD-mode decision (ADR 0002). Download the populated zip.
The scaffold uses handoff.md for cross-session state tracking — not for your idea. If GSD is installed, STATE.md at the project root takes over that role.
03

Land it on your machine.

From browser-zip to a real project folder you can build in.

  1. Unzip into a project folder. Rename the top folder to your project name. Put it somewhere predictable — ~/code/, ~/Projects/, your call.
  2. Initialize git and push. 
    git init
git add .
git commit -m "scaffold: initial project structure"
# then create a repo on GitHub and:
git remote add origin <your-repo-url>
git push -u origin main
    Now you have a snapshot to roll back to before you (or any AI) touches anything.
  3. Open it in your editor + CLI. VS Code, Cursor, whatever you use. Start your AI CLI in the same folder.
04

Orient. Read everything.

Most "AI got confused" stories trace back to skipping this step.

Before you ask the AI to build anything, have it read — and have you read — AGENTS.md, README.md, external/GSD-INTEGRATION.md, the seeded ADRs in 02-notes/decisions/, and the handoff log. Understand how the pieces talk to each other. Five minutes here saves hours later.
  1. Have the CLI summarize the scaffold back to you. "Read AGENTS.md and the planning docs, then tell me in five bullets how this project is meant to be run." If the summary is wrong, fix the docs before coding.
  2. Lock in the GSD mode decision. ADR 0002 has three checkboxes: GSD-led, docs-led + GSD execution, or no GSD yet. Pick one. Don't run /gsd-new-project until this is decided.
05

Install GSD (optional but recommended).

GSD adds structured spec-driven workflow + subagent orchestration so long sessions don't fall apart from context rot.

  1. Install from the maintained fork. Use the open-gsd version — not the legacy one. 
    npx @opengsd/get-shit-done-redux@latest
    Repo: github.com/open-gsd/get-shit-done-redux · The original upstream had a trust incident; the open-gsd team maintains the current version.
  2. Restart your CLI. Required, every time, for the new commands and skills to register.
  3. Kick off the project. 
    # bringing GSD to a fresh project:
/gsd-new-project

# bringing GSD to an existing codebase:
/gsd-map-codebase
/gsd-new-project
    If you chose GSD-led mode, expect AGENTS.md, PROJECT.md, REQUIREMENTS.md, ROADMAP.md, and STATE.md to be written or rewritten by GSD at the project root.
06

Build the loop. Ship in small steps.

With GSD, every cycle is the same six beats. Without GSD, the rhythm is the same — just hand-driven through the planning docs.

  1. Plan the phase. With GSD: /gsd-discuss-phase 1 then /gsd-plan-phase 1. Without: write the spec in 01-features/<name>/ before any code.
  2. Execute. /gsd-execute-phase 1 — runs in parallel subagent waves, atomic commits per task. Without GSD: prompt your CLI against the spec, one focused change at a time.
  3. Verify. /gsd-verify-work 1, or manual acceptance against your spec. Code that runs is not code that works.
  4. Ship and update the baton. /gsd-ship 1 or commit + open a PR. Then update the handoff log (or let GSD update STATE.md) so the next session — yours or another CLI — picks up clean.
  5. When confused, ask in a fresh session. "How does this scaffold work?" or "What does external/GSD-INTEGRATION.md say I should do next?" A new session with the right context beats a long one with rotted context.
One driver per branch. Don't run Codex and Claude editing the same files at the same time. Commit before switching tools, update the handoff log, then hand off.
★ Bonus

Level it up.

Once the basic loop feels comfortable, these turn it up a notch.

  • Brainstorming skills during planning. Plugins like the Superpowers collection add a dedicated brainstorming skill that pairs well with the GSD planning step — it pushes you to consider edge cases and alternatives before the plan locks in.
  • Match the model to the task. Use your highest-reasoning model (e.g. GPT-5.5, Claude Opus) during planning and verification — these steps are where deep thinking pays off. Switch to a faster, cheaper model for execution; that step is mostly mechanical once the plan is solid.
  • Git worktrees for true parallel runs. If you really do need two CLIs working at once, give each its own branch via git worktree instead of fighting over the same files.
  • Keep an ADR habit. Every real tradeoff goes in 02-notes/decisions/. Future-you (and every AI session) needs to know why, not just what.
